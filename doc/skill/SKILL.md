# skill：项目规范检查与规范生成

两个模式，按用户意图路由：

- **模式 A：规范检查**——用户提供了代码片段或文件路径，要求对照项目规范检查。规范文档存在时直接使用；不存在时先提示并转入模式 B（或对既有代码做约定归纳）。
- **模式 B：规范生成**——项目缺少规范文档，或用户要求生成/更新规范文档。从仓库**真实代码**与既有文档归纳，不套用通用模板。

详细操作流程见 `references/` 下两个文件，按模式加载对应文件：

- 模式 A → 读 `references/spec-review-checklist.md`
- 模式 B → 读 `references/spec-generation-guide.md`

## 模式 A：规范检查（核心流程）

1. **定位规范文档**：按顺序查找 `DEV_SPEC.md`（仓库根）、`doc/开发规范和编码指南.md`、`CONTRIBUTING.md`、`README.md` 中指向的规范链接。找到后读取全文（长文档分段读）。找不到时告知用户并询问：转入模式 B 生成，还是仅按代码库现状归纳检查。
2. **获取待检代码**：用户粘贴的片段直接用；给了文件路径则用 Read 读取；给了目录/模块则 Glob + Grep 逐文件扫描，先确认文件数量，超过 20 个文件时与用户确认范围。
3. **执行六项检查**（详见 `references/spec-review-checklist.md`）：命名、文件放置与导入路径、分层/组件写法与类型定义、禁止事项、问题清单与修改建议（每条带规范原文依据）。
4. **输出纪律（不可违反）**：
   - **只报真实违规**：规范文档没有规定的，不额外强加个人风格，不引用外部"最佳实践"当依据；
   - 每条问题必须给出：位置（文件:行号）、违反的规范章节与**原文引用**、修改建议；
   - 规范中标注【待团队统一】或【不一致点】的条目是"两可"状态：两种写法都不算违规，除非用户明确选择了其中一种；
   - 同一问题多处出现时归并为一条，列出全部位置；
   - 最后给一个简短结论（合规 / N 处违规，按严重度排序：结构红线 > 禁止事项 > 命名与写法）。

## 模式 B：规范生成（核心流程）

1. **盘点**：读 README、既有规范/指南文档（若存在则以它为底稿）、构建文件（pom.xml/package.json 等），确认技术栈与模块划分。
2. **抽样验证**：对每类约定（分层、命名、返回体、错误处理、Git 提交）读取 2~3 个真实文件核实；用 `git log --oneline` 核对提交与分支现状。**规范必须来自代码现状，不来自想象。**
3. **写文档**：章节结构参见 `references/spec-generation-guide.md`；主流写法入规范，少数派写法标【不一致点】并给出推荐项；无统一实践处标【待团队统一】，禁止编造规则。
4. **同步引用**：文档落位后（根目录 `DEV_SPEC.md` 或 `doc/` 下），更新 README 等处的引用链接；替换旧文档时保留跳转存根或确认删除。

## 边界

- 检查只读代码与规范文档，不主动修改业务代码；修改建议以清单形式给出，经用户确认后再改。
- 规范文档的修订（含删除待修正项）按用户明确指示执行，不自行裁决冲突条款。
