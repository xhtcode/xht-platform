# 模式 B：从真实代码生成项目开发规范文档

## 目标

产出一份"描述本项目当前实际执行的约定"的规范文档——所有规则都能在仓库代码中找到出处，而不是通用最佳实践清单。

## 文档章节结构（默认模板，可按项目裁剪）

1. **项目概述**：用途、技术栈表（语言/框架/版本取自构建文件）、服务与启动类清单、术语表
2. **目录结构与模块职责**：模块全景树、分层职责表（每层只允许放什么/禁止什么）、依赖方向图、包结构实例、"新增代码该放哪里"对照表
3. **命名规范**：类名后缀表、包命名、方法命名表、变量/常量、数据库命名、缓存 Key、配置项前缀
4. **代码写法规范**：各层代码模板（取自真实文件）、依赖注入方式、事务边界、日志、缓存、用户上下文等横切约定
5. **接口请求规范**：路径风格（如实统计现有 Controller 的实际风格并写明统计口径）、入参校验、返回体结构、错误码与异常、权限注解、服务间接口配对
6. **组件开发规范**：可复用单元（starter/公共包/客户端装配等）的命名、落位、装配模板
7. **Git / 提交规范**：提交格式（与 `git log` 实际一致，必要时标注不一致点）、分支模型（以远端实际分支为准）、测试要求
8. **新增功能开发流程**：从建表到联调的编号步骤，落到具体模块路径
9. **禁止事项 & 踩坑提醒**：结构红线、安全红线、依赖与配置红线、高频坑（来自代码中实际存在的防御机制，如拦截器、自动填充、序列化器）

可附附录：正反例速查表、Code Review 检查清单、代码待修正清单（列出"文档与代码现状不一致、待改"的项，**只登记不裁决**）。

## 生成流程

1. **盘点**：读 README 与既有文档；读根构建文件与各模块构建文件，确认模块清单、依赖版本、父工程关系；`git branch -a` + `git log --oneline -15` 核对分支与提交格式现状。
2. **按类抽样**：每类约定找 2~3 个代表性文件验证——一个 Controller、一个 Service 接口与实现、一个 DAO/Mapper、一个 Converter、一个 Entity、一份公共契约、一个自动装配类。用 find/Glob 列出同类文件后核对命名分布（如 Controller 路径风格用 grep 统计）。
3. **识别不一致点**：同一约定存在多种写法时，统计哪种是主流（多数文件采用者），主流入规范，少数派标【不一致点】并写明"新增统一用 X，存量不强制改名"。
4. **标注待统一**：文档与代码冲突、或团队尚无统一实践的地方，标【待团队统一】，不得替团队做决定（例如分支名、commit 是否带 scope）。
5. **落盘与同步**：
   - 默认写到仓库根 `DEV_SPEC.md`；用户指定 `doc/` 路径时按用户要求；
   - 替换旧文档时，把旧文档替换为跳转存根或经确认后删除，并更新 README 等处的全部引用（含章节号引用，章节号按新结构改写）；
   - 文档头部写更新日期。

## 质量红线

- 每条规则必须能指出至少一个真实代码出处（文件名即可），写不出出处的规则删除或标【待团队统一】；
- 不复制网上模板的措辞；示例代码一律取自仓库真实文件（可裁剪）；
- 版本号、端口、启动类名等事实性信息以构建文件与代码为准，不以 README 记忆为准（README 可能滞后）。
